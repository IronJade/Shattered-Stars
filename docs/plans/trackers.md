# Plan: tracker support (Universal Tracker and PopTracker)

Written 2026-10-26 by the agent "trackers" at the user's request. This is the new **Phase B** of
docs/plans/next.md: it replaces the port 0.03.00 Japan-disc work there. Phase A (the tests guide)
still comes first, and Phase C (entrance randomizer) after this one (see "Phase C" below).
Research log: docs/handoff/trackers.md. Scratch scripts: scratchpad/trackers/.

> "I was approached with someone asking about integrating with
> https://github.com/FarisTheAncient/Archipelago.git or outputting FOR it. [...] The other is
> outputting to https://github.com/black-sliver/PopTracker.git ... look at outputting correctly for
> these two popular trackers? Let me know what they need and what our best plan of action would be
> to get them functional with our game." (the user, 2026-10-26)

## In short

- **FarisTheAncient/Archipelago is Universal Tracker (UT)**, an Archipelago client (`worlds/tracker`,
  branch `tracker`, v0.3.6 of 2026-10-25, AP >= 0.6.2). It needs no export from us. It loads
  so2.apworld itself, builds the world again on the player's machine and evaluates *our own* rules
  against what the server says was received and checked. What it needs from a world is that the
  rebuilt world is **the same world**. UT uses a fresh random seed, so every random choice that shapes
  locations or rules must come back from `slot_data`.
- **Our world is close.** The only random choice that shapes logic is the party pool, and slot_data
  already has it (`characters`). A proof of concept (scratchpad/trackers/ut_poc.py) monkeypatches the
  proposed change: options and party restored from today's slot_data, yaml-less. It matched the real
  generation in every sphere for 7 option mixes x 2 seeds (all three world modes). Today, without the
  change, any `character_items` mix drifts by 30 to 130 locations (scratchpad/trackers/ut_desync.py).
  **UT support is about 80 lines in world.py plus a test.** It can ship as world 0.2.1 and also works
  for rooms generated with 0.2.0 (same data package).
- **PopTracker** (black-sliver/PopTracker, v0.36.0 of 2026-10-25) is a stand-alone tracker that runs
  *packs*: JSON (items, locations with access rules, maps, layouts), images and Lua. It connects to
  the AP server as a tracker. It cannot run Python, so the logic has to be in the pack. The
  recommended way to get it there without copying our logic into Lua by hand is this. The world writes
  its resolved logic for the seed (rules as data) into slot_data. A generic Lua evaluator in the pack
  reads it. The pack is **generated by a script in this repo** from the apworld's own tables, so ids,
  names and areas stay in sync. A cleaner rules-as-data form (AP's Rule Builder) also gives UT its
  `/explain` output and gets Phase C ready.
- **No disc assets.** The pack and the UT map tab use **original images only**: script-drawn
  schematic world maps with area dots placed from the world-map arrival coordinates in
  docs/ap/doors.json, check boards, and text badges for items. Players can put their own images in
  PopTracker's `user-override/<pack_uid>/`.
- **The port needs nothing for basic tracking.** Items and checks already go through the server.
  Optionally it can publish its current map and story position to data storage, for automatic map
  tab switching (PopTracker and UT) and story-aware tracking. This is written only during a connected
  AP run, so "AP off = the disc's game untouched" holds.

## 1. Universal Tracker: what it is and what it needs

Sources: the clone at scratchpad/trackers/ut (FarisTheAncient/Archipelago, branch `tracker`, commit
abe7202 of 2026-10-24; `worlds/tracker/archipelago.json`: version 7, minimum AP 0.6.2;
`__init__.py:26` UT_VERSION v0.3.6). Docs read in full: `worlds/tracker/docs/apworld-integration.md`,
`re-gen-passthrough.md`, `map-integration.md`, `client-integration.md`, `setup.md`. Releases:
https://github.com/FarisTheAncient/Archipelago/releases (Tracker_v0.3.6 is the latest; the separate
Tracker_Addons_v0.1.4 adds commands).

**How it works.** The player installs `tracker.apworld` beside our `so2.apworld` and opens
"Universal Tracker" from the Launcher. It connects like a text client: tags `AP` and `Tracker`,
`game=""`, items_handling 0b111 (TrackerClient.py:350, :1799, :37). On `Connected` it builds an
internal MultiWorld (TrackerCore.py:380 `TMain`):
- `multiworld.generation_is_fake = True` (:397). There is **a new random seed** (`set_seed(seed, ...)`
  from Generate's own roll, :403), and the options come from the player's YAML in UT's players folder,
  or from slot_data when the world is yaml-less.
- It runs only `generate_early, create_regions, create_items, set_rules, connect_entrances,
  generate_basic` (:384-391). No pre_fill, fill, fill_hook, post_fill, fill_slot_data or output.
- It drops precollected items that have codes (:366-370). The server sends them as received items.
- `updateTracker` (:419) collects the received items through our `create_item`, sweeps our events
  and lists the locations that are reachable *and* still missing on the server. So a location that
  exists on the server but not in UT's world can never show up, and a rule that differs shows the
  wrong thing.

**The hooks a world can offer** (apworld-integration.md, re-gen-passthrough.md):

| Hook | What it does | For us |
|---|---|---|
| `interpret_slot_data(slot_data)` | called after connecting. Return non-None to regenerate with `multiworld.re_gen_passthrough = {game: returned}` | yes: a `@staticmethod` returning slot_data |
| `ut_can_gen_without_yaml = True` | skip the first YAML generation; generate once from slot_data alone (an empty YAML, then the passthrough) | yes: no YAML for the player to install, "random" options are fine |
| `generation_is_fake` | lets the world skip useless randomness or create every possible location | not needed |
| `disable_ut` | refuse UT | no |
| `location_id_to_alias` | adds a per-slot alias to a location's line | optional |
| `custom_ut_sort(region, location)` | sort key for the tracker tab (host.yaml `sorting_method: apworld`, the default) | yes, cheap: story order, then area |
| `glitches_item_name` | "glitched" (out-of-logic but possible) display | not applicable |
| `get_logical_path`, `explain_rule`, `explain_more`, `explain_path`, `explain_spot` | override `/get_logical_path`, `/explain`. The default `/explain` uses the **Rule Builder** (`rule_builder`, AP core since 0.6.7) | free once our rules are Rule Builder rules (B2) |
| `tracker_world = {...}` (ClassVar dict) | a **map tab** in PopTracker's JSON format: maps.json, locations.json (section names = AP location names), images. Internal (in the apworld), external (a PopTracker pack zip the user selects) or hybrid. Auto tab switching from a data-storage key (`map_page_setting_key` with `{player}` / `{team}` placeholders, `map_page_index(data) -> int`). A player icon (`location_setting_key`, `location_icon_coords`). Item panels (`item_page_items`, layouts) | B6 |
| `found_entrances_datastorage_key` + `reconnect_found_entrances(key, value)` + `multiworld.enforce_deferred_connections` ("on" / "default" / "off", host.yaml `enforce_deferred_entrances`) | **deferred entrances and events**: hanging entrances connected only when the client reports them in data storage. Used for ER without spoilers, and to mirror real game progress as events | Phase C (ER). Story-mode story progress (B6, optional) |
| `ut_map_page_hidden_locations` / `_entrances` / `_events` | hide things per map page | as needed |
| fuzzer hooks `worlds.tracker.fuzzer_hook:Hook` / `:YamllessHook` | with Eijebong/Archipelago-fuzzer: generate, then replay the server's spheres through UT and fail on any difference | the model for our own test (B1) |

Reference integrations upstream: Tunic (scratchpad/ap/Archipelago/worlds/tunic/ut_stuff.py:
yaml-less option restore, deferred ER entrances keyed `Slot:{player}:<portal>`, map tab from an
external pack, auto-tab key `Slot:{player}:Current Map`), Timespinner, Mario Land 2, The Witness, OSRS,
Satisfactory, Jak and Daxter (`ut_can_gen_without_yaml` in worlds/*/__init__.py).

UT also works as a library (`TrackerCore`, client-integration.md) and from the command line
(`Launcher.py "Universal Tracker" -- --nogui --count Slot:pw@host`), which makes a scripted check
against a local server possible (B1 verification).

## 2. PopTracker: what it is and what it needs

Sources: the clone at scratchpad/trackers/poptracker (black-sliver/PopTracker master 575ee4b of
2026-10-25, release v0.36.0). Read: `doc/PACKS.md`, `doc/AUTOTRACKING.md`, `doc/PackCreation.md`,
`doc/commandline.txt`, `examples/ap-storage-example`, `src/ap/aptracker.h`. The usual AP starting
point is the template pack (https://github.com/Cyb3RGER/template_pack, the `examples/template_pack`
submodule; cloned to scratchpad/trackers/template_pack). The JSON scaffolding generator is
https://github.com/StripesOO7/poptracker-pack-builder. The pack list is the `packlist` branch
(scratchpad/trackers/packlist). A large real pack to compare with is the Pokemon Emerald AP pack
(scratchpad/trackers/emerald).

**The pack format.**
- `manifest.json`: `name`, `game_name`, `package_uid`, `package_version`, `platform`, `author`,
  `variants` (each with `display_name` and `flags`; the flag `"ap"` enables AP autotracking),
  `versions_url` (auto-update), `min_poptracker_version`, `target_poptracker_version`. Avoid the flags
  `"apmanual"` (lets the pack send location checks) and `"aphintgame"`: our port counts the server's
  checks as its own (engine/src/game/ap/ap.cpp:1620-1629).
- `items/*.json`: `toggle`, `progressive`, `consumable`, `static`, `composite_toggle`,
  `toggle_badged` items, each with `codes` and `img`.
- `locations/*.json`: a tree of locations (each with `map_locations` {map, x, y}) and **sections**
  (the checks, `item_count`). Each has `access_rules` and `visibility_rules`: a list of
  comma-joined AND groups, OR'd. Codes count items; `$func|arg` calls Lua; `@loc/section` refers to
  another rule; `[...]` marks optional (sequence-break) and `{...}` inspect-only.
- `maps/*.json` + images, `layouts/*.json` (`tracker_default`, `tracker_broadcast`, tabs, item
  grids, maps), optional `settings.json`.
- Lua from `scripts/init.lua`: `Tracker:AddItems/AddMaps/AddLocations/AddLayouts`,
  `Tracker:FindObjectForCode`, `Tracker:UiHint("ActivateTab", name)`, `ScriptHost:AddWatchForCode`,
  `Tracker.BulkUpdate`.

**AP autotracking** (AUTOTRACKING.md "Archipelago Interface"): `Archipelago:AddClearHandler(name,
f(slot_data))`, `AddItemHandler(f(index, item_id, item_name, player))`, `AddLocationHandler(f(id,
name))`, `AddScoutHandler`, `AddBouncedHandler`, `AddRetrievedHandler(f(key, value))`,
`AddSetReplyHandler(f(key, value, old))`, `Archipelago:Get(keys)` / `:SetNotify(keys)` (call them in
the Clear handler), `.PlayerNumber`, `.TeamNumber`, `.CheckedLocations`, `.MissingLocations`
(filled before the Clear handler runs: aptracker.h:126-133). It connects with tags `PopTracker`,
`NoText`, `Tracker` and items_handling 0b111 (aptracker.h:397-407). The template maps AP ids to pack
codes with `ITEM_MAPPING[id] = {{code, type}}` and `LOCATION_MAPPING[id] = {{"@Area/Location/Section"}}`
(scripts/autotracking/item_mapping.lua, location_mapping.lua). It also highlights hinted locations from
the read-only key `_read_hints_{team}_{slot}`.

**Option-dependent location sets.** Packs read the options from slot_data in the Clear handler and
set "setting" items that `visibility_rules` test (Emerald: archipelago.lua:61-76). A pack can also
show only the locations the room actually has (`MissingLocations` and `CheckedLocations`). Variants
are for presentation the user picks (map tracker / items only / vertical), not for game options.

**Current map / game state.** Two conventions upstream. One is a **data-storage key** the game client
writes: Tunic `Slot:{player}:Current Map`, SMW `smw_curlevelid_{team}_{slot}`, MLSS
`mlss_room_{team}_{slot}`, MM2/MM3 progress keys, Emerald `pokemon_emerald_events_{team}_{slot}`. The
other is a **Bounce to the own slot** (Emerald `MapUpdate`, client.py:431-440). UT's map tab supports
only data-storage keys, and a key also persists for a tracker that connects later, so we use keys.

**Distribution.** Usually the pack has its own GitHub repo. The zip is a release asset, and
`versions.json` (package_version, download_url, sha256, changelog) is published at a raw URL (often a
`versions` branch) that `manifest.versions_url` points to. Listing in the `packlist` branch's
`community-packs.json` (a PR; checklist.md: the uid must match, https URLs, authorship) makes it
installable from inside PopTracker (`--install-pack <uid>`). Validation in CI:
`PopTracker/pack-checker-action` (the template's `.github/workflows/validation-strict.yml`).

**Images and copyright.** Most community packs ship rips of the game's maps and sprites (Emerald's
`images/` is 31 MB). UT's map doc advises against map images inside an apworld ("copyright and file
size concerns"). Our rule is stricter: nothing from the discs in git or in anything we publish
(docs/HANDOFF.md "Conventions to keep"). So we use original images only, plus PopTracker's **user
overrides** (README "User Overrides": `Documents/PopTracker/user-override/<pack_uid>/...` replaces
pack files, images included) for anyone who wants their own.

## 3. Our world, from a tracker's point of view

### 3.1 Randomness that shapes locations, items, regions or rules

| Where | What | Shapes | In slot_data today? | For UT |
|---|---|---|---|---|
| world.py:150-169 `choose_open_party` (rng.sample / choice, :163, :167-168) | open world and hub: the character pool (and the healer guarantee) | which killer-move, craft and learn-point locations exist and their DEFAULT / EXCLUDED type (locations.py:113-153, skillsanity.py:163-182), killer-move rules (rules.py:249-273), `progression_characters`, skill needs (skillsanity.py:226-247) | **yes**: `characters` (world.py:350) | restore it |
| world.py:171-186 `choose_party` (rng.choice, :183, :185) | story mode with character_items: the pool | as above | **yes**: `characters` | restore it |
| hub.py:378-384 `choose_start` (random_town, :383) | the hub's start town | the seed's `hub.start` only. No region, location or rule (both towns connect from Menu, hub.py:268-269) | **yes**: `hub_start_town` | restore it anyway (display, sort) |
| world.py:253, :259-260, :277, :283-284 | which filler becomes an area key, dungeon key, character or trap | item placement only | n/a | harmless: UT never fills, the server tells it what was received |

- `hub.fienal_won` (hub.py:205-218) and `hub.needed_keys` (hub.py:221-230): from the options and `chosen`.
- `skillsanity.plan` (skillsanity.py:226-247): from `chosen` and `party.guaranteed`.
- The rules (rules.py, regions.py, hub.py:331-374, skillsanity.py:260-327): from the options, the party and the data tables.

**Every option is in slot_data already** (world.py:338-378): goal, world_mode, expel_teleporter,
shuffle_shops, story_route, missable_locations, expel_progression, cave_of_trials, boss_checks,
character_items, enemy_dropsanity, traps, the multipliers, encounter_rate, difficulty, death_link,
drop_progression, area_keys_in_drops, craftsanity, no_fail_crafting, killer_move_checks,
killer_move_progression, skillsanity, skillsanity_shop_share, exclude_characters, and in hub mode
hub_start, fienal_requirement, fienal_won, dungeon_keys. Most use the option's `current_key`, so
`Option.from_any` reads them back. Some need care:
- `starting_character` is *transformed*: a name, `None` (hero) or the select's list (any). The reverse
  map is None -> hero, list -> any, name -> its key.
- `expel_teleporter` is `open_world and bool(...)` (only read in open world).
- `character_items` is forced True in hub mode.
- Not in slot_data: the common options. `exclude_locations` only changes UT's "excluded" display.
  `start_inventory` comes from the server as received items. Adding `exclude_locations` is optional and
  cheap.

**Measured** (AP 0.6.8 in scratchpad/ap, run from scratchpad/ap/Archipelago with `PYTHONPATH=.`):
- `ut_desync.py` regenerates with the same options but other seeds, which is UT today with the
  player's YAML. Story mode at defaults matches. With character_items the party is re-rolled. Story
  mode (`story chars+crafts+killers`) has up to 67 locations missing and 81 extra; 2 of 5 seeds
  matched by chance. Open world and hub have 28 to 133 missing or extra in every seed. Reachability
  differs for up to 88 locations.
- `ut_poc.py` simulates UT's TMain: default options, `generation_is_fake`, `re_gen_passthrough`, another
  seed. It patches generate_early to restore the options and the party from the JSON round-tripped
  slot_data. Mixes: story default; story + characters/crafts/killers/skillsanity insanity; open world
  full (shops full, drops, Iseria Queen goal, Rena's route, no teleporter); open world with
  starting_character any / Noel and excluded members; hub full (random_town, all_bosses); hub fields
  on Claude's route. For each, two seeds: **0 missing locations, 0 extra, every sphere identical**.
  This is the fuzzer hook's check without UT installed.
- Every item name in the data package goes through `create_item` in all three modes (UT creates
  received items by name).

### 3.2 Ids, tables, groups

- Ids are static class attributes: `item_name_to_id = items.ITEM_NAME_TO_ID` (1,297 items) and
  `location_name_to_id = locations.LOCATION_NAME_TO_ID` (1,991 rows, unique ids
  1347569664..1374817287), built from data tables at import (locations.py:31-33). Per type: 308 chests,
  101 gifts, 21 joins, 42 bosses (+ the hub's own rows), 89 first drops, 550 shop slots, 553 crafts,
  133 killer-move levels, 45 skill-guild checks, 149 learn points.
- A world has 359 locations at the defaults, and about 1,860 in open world with every check option on.
  Hub at full options: about 1,160 (about 1,630 with every shop slot).
- Location groups: 117 (per region, per area, per type, "Boss Chambers", per specialty, per member's

- Location names are `"<Area>: <thing>"`. There are 71 areas; 35 key groups (open world's area keys,

### 3.3 Logic shape

- **Story mode** (regions.py:36-60): Menu -> Expel -> Energy Nede -> Fienal -> Cave of Trials on three
  events that have **no item requirement** in story mode. So almost everything is in logic from the
  start. The only real rules are killer moves (stage events, a character item, a move item:
  rules.py:249-273), crafts and learn points under skillsanity (skill items: skillsanity.py:260-327)
  and the Iseria Queen's song. A tracker's value here is the checklist by area. It gets far better
  with story awareness, which needs the port's chapter (B5/B6).
- **Open world** (regions.py:78-102, rules.py:127-166, :298-353): 23 story-stage events chained on
  area keys, the El voyage gate's keys added to its stage (data.STORY_GATES), the teleporter event
  (stage 16 + Fun City Pass) and the Final Save Point (the last stage). A location's rule is an OR of
  (stage event, keys) modes, and drops have their own modes. **Every event reduces to items**, so it
  can be written from items alone, but the rule *data* depends on story_route (the proofs per game),
  expel_teleporter and expel_progression (the gate's teleporter keys).
- **Hub** (hub.py:258-374): Menu -> both towns. A region per keyed dungeon, entered with its key.
  Fienal is opened by the event that needs the requirement's dungeon keys. Drops need any of their
  dungeons' access. Killer moves: Fienal open past level 30. Plus the goal events.
- No rule reads region reachability (no `can_reach`), so there are no indirect conditions today.
  Phase C will need them.
- Nothing needs story *state* beyond what items imply: the El voyage and the disc switch are logic
  events with port gates. What a tracker cannot know from items is the *actual* story position in
  story mode, the hub chambers' fights outside boss_checks, and where the player is. Only the port can
  publish those (B5).
- Size of the rule code: rules.py 357, regions.py 102, hub.py rules ~150, skillsanity.py rules ~110
  lines. A hand port to Lua would copy about 400 lines of Python plus the data tables, and would have
  to be kept in step by hand. Exported per seed as data, it is a few dozen KB. A rough estimator,
  scratchpad/trackers/rule_size.py, reads the lambdas' captured `modes` / `need` / `ways`. At the
  richest open-world mix: 1,865 locations, 180 distinct rule bodies, about 48 KB of plain JSON
  (location map about 30 KB, rules 18 KB). Hub full: about 29 KB. Story: about 5 KB. A compact
  encoding (rule index per sorted id) roughly halves it.

### 3.4 Maps, names, coordinates (and the no-assets rule)

- Map names: docs/modding/reference/map_names.csv (964 maps: `map, disc, area, place, kind`), so the
  pack can map a field map id to an area / tab.
- World-map positions: docs/ap/doors.json `arrivals` on maps 1 (Expel) and 2 (Energy Nede) give the
  world-map x/z where the party appears when leaving an area. That is 49 arrivals covering the 35
  areas entered from the world maps (x 8,713..103,823, z 12,973..68,421). These numbers are enough to
  place an area's dot on a **script-drawn schematic** of each world. That is original art from factual
  coordinates, not a trace or a rip, and it is a decision for the user (D5).
- docs/ap/field.json (maps, chests by map and flag), late_proof.json / hub_proof.json (what is reached
  where) and doors.json (the door graph) have no positions of chests inside a map. So the pack places
  checks **per area** (a popup listing the area's checks), not per chest.
- Checks that are not places (shops, crafts, killer moves, skill guilds, learn points, enemy drops)
  go on generated **boards** (grids of labelled cells), one tab each.
- Item icons: generated text badges (category colour + short name), drawn by the generator (PIL 12
  is installed), like tools/make_icon.py's original art.

### 3.5 The port as an AP client, next to a tracker

- engine/src/ap_net/client.cpp:158-161 connects with items_handling **0b001** (link.h:24: our own
  items are given offline from the seed) and tags `DeathLink` only. Trackers connect with 0b111, so
  they still receive our own-world items and the starting inventory from the server. Several
  connections to one slot are normal in AP. The server sends `start_inventory + items` to 0b111
  clients (MultiServer.py:2075). Trackers send no checks (the server refuses LocationChecks from
  `Tracker` clients: "Trackers can't register new Location Checks", MultiServer.py:2078-2082).
  Nothing in our client trips over a second connection.
  Trackers need the room's password like any client.
- The port sends every check (ap.cpp:993) and queues them while offline, resending on reconnect
  (ap.cpp:1629). So offline play shows up in a tracker only once the port reconnects. The player
  guide should say so.
- It writes **no data storage** today, and nothing else reads slot_data: the port takes its options
  from the .apso2 (seed.cpp:400). Adding slot_data keys is safe for the port.
- It knows the story position (chapter G[0xa0], step G[0xa4]: ap.cpp:428), the map id and the world-map
  position, so it could publish them (B5).
- The rule "AP off = the disc's game untouched" (memory ap-off-is-natural; docs/HANDOFF.md) is about
  AP-off and no-seed runs, and the ban on debug hooks in AP runs. Data-storage writes made only while
  a seed is loaded and the slot is connected (`r.link && r.net_ok`) change neither. They are not
  debug hooks either.

## 4. Design choices (with the reasons)

1. **UT: yaml-less regeneration from slot_data** (Tunic's pattern). With
   `ut_can_gen_without_yaml = True` and a static `interpret_slot_data`, UT never reads a YAML for our
   game. The world restores the options and the party at the top of `generate_early`. Rooms from 0.2.0
   work too, because their slot_data already has all of it.
2. **Rules as data** (AP's Rule Builder, `rule_builder/`, docs/rule builder.md; in AP 0.6.7+, our
   minimum is 0.6.8). The rule sites become `Has` / `HasAll` / `HasAny` / `And` / `Or` / `True_`
   rules set with `world.set_rule`. Item rules (`add_item_rule`) stay as they are. In return:
   - UT's `/explain` and `/get_logical_path` work;
   - the resolved rules are plain dataclasses we can export (B3);
   - Phase C's Generic ER gets its indirect conditions registered automatically for rules that read
     regions.

   The fallback, if the user would rather not migrate: record the rule data (modes / needs / ways) at
   each rule site next to the lambdas. That is smaller, but gives no `/explain`.
3. **PopTracker logic from slot_data** (recommended) rather than a Lua port. The world writes a
   compact, interned export of its resolved logic into slot_data: regions, entrances, events and each
   location's region and rule, with items by AP id. The pack's Lua is a generic evaluator (a region
   sweep plus Has/All/Any/And/Or, about 150 lines) and contains no game logic.
   - Pros: exact parity with the apworld by construction, for every option and every future logic
     change, ER included (the export is the post-ER graph). One pack for all modes.
   - Cons: about 25-50 KB more slot_data per connect (the port ignores it). Rooms generated before the
     export get no logic in PopTracker: checklist only. The pack cannot preview logic before
     connecting.
   - The alternative (L2): generated per-variant tables (open world: story_route x teleporter x
     expel_progression) plus about 250 lines of Lua for the party, skill, killer-move and hub pieces.
     It works with 0.2.0 rooms, but duplicates the logic and has to be redone for ER.
4. **One generator, two outputs.** `tools/ap_poptracker.py` (in this repo) reads the apworld's tables
   (locations.ALL_ROWS, item ids and groups, data.KEY_GROUPS / HUB_DUNGEONS / STAGES), map_names.csv
   and doors.json. It writes:
   - (a) the PopTracker pack, a zip under `dist/`;
   - (b) the UT map tab files into `apworld/so2/tracker/` (maps.json, locations.json, the original
     PNGs), which go into so2.apworld.

   PopTracker section names are the AP location names, or shortened with UT's
   `poptracker_name_mapping`, which the generator writes too. So one set of JSON serves both trackers.
5. **Data-storage keys from the port** (B5). They are written only while connected with a seed, and
   only when the value changes:
   - `so2_map_{team}_{slot}`: `{"map": id}`, plus `x` / `z` on a world map, throttled, for UT's
     player icon;
   - `so2_story_{team}_{slot}`: `{"chapter": c, "step": s}`, on a chapter change;
   - later, `so2_entrances_{team}_{slot}`: a list of the transitions found (Phase C).

   UT spells them `so2_map_{team}_{player}`. Lower-case and game-prefixed, like `smw_` / `mlss_`.

## 5. The plan (Phase B)

each with its own docs/handoff/<name>.md. Model choice: the world and design pieces (B1-B3) on the
strongest model; the generator's bookkeeping parts and packaging can go to a cheaper one.

### B3. Logic export for trackers (world 0.2.2) — size S-M

- `fill_slot_data` gains `"tracker": {format: 1, items: {...ids used...}, regions: [...],
  entrances: [[from, to, rule]], events: [[name, region, rule]], locations: {id: [region, rule]}}`.
  Rules are interned (a table of unique rule bodies; locations point at them) and items are by AP id.
  It is produced by walking the resolved rules (dataclasses) of every location, entrance and event.
  Not in the .apso2's `options` copy: seed_data drops it.
- A Python reference evaluator of the export (tools/, also imported by the tests) is checked against
  the world's own logic sphere by sphere, for every B1 mix. A size test keeps it at or under about
  64 KB at the richest mix.
- Size: about 150 lines plus tests.

## 6. Phase C (entrance randomizer) and the trackers

- **UT and ER.**
  - The pairings from `randomize_entrances(...).pairings` go into slot_data, as Phase C already plans.
  - In UT mode (`re_gen_passthrough` present), `connect_entrances` connects from the pairings instead
    of randomizing (Tunic's pattern), and bumps `logic_version`.
  - Non-spoiling play: deferred entrances. With `enforce_deferred_connections` not "off", leave the
    randomized entrances hanging, `found_entrances_datastorage_key` = `so2_entrances_{team}_{player}`
    (or a key per entrance), and `reconnect_found_entrances` connects what the port reports.
  - The port writes a transition to that key the first time a redirected door is used. That is a small
    addition on top of B5's `Link::set`.
- **PopTracker and ER.** The B3 export carries the post-ER region graph, so the pack's evaluator
  handles ER with no change: regions, entrances and the region sweep are already in format 1. For
  non-spoiling display the pack shows a pairing only once it is in the entrances key.
  `poptracker_entrance_mapping` / entrance sections serve UT's map tab.
- **Shared groundwork.** The area table B4 builds is what er-model needs for its entrance table:
  world-map entrances per area, arrivals and positions. B2's Rule Builder provides the indirect
  conditions Generic ER requires. Build them once and share.
- Phase C's decision 5 ("tracker support: the pairings in slot data; whether a PopTracker pack is in
  scope") is answered by this phase: yes, and the pairings plus the found-entrances key cover both
  trackers.
