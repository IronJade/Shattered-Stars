# Submitting a Mod

Made a mod you'd like others to play? Submit it to the project's **curated list**, and once the
maintainer has verified it with the real game, players can find it there. This page covers the
whole process: the pull request, the automatic check, the maintainer's verification, and
updates.

Make and test your mod first: see [Making a Mod](Making-a-Mod).

## The curated list

The list lives in the
[mods folder](https://github.com/IronJade/Shattered-Stars/tree/main/mods) of the repository:

```text
mods/
  README.md            how to submit
  index.json           every mod, the sha256 of each of its files, and whether it is verified
  arlia-crate-fol/     one folder per mod, named after its id
    mod.json
    crate.patch
    README.md
  hearn-store-plus/
    ...
```

`index.json` is generated by `port/tools/mod_index.py` from the mod folders. **Only the mods with
`"verified": true` in `index.json` are on the list.** A submitted mod starts unverified.

### What "verified" means

The maintainer ran `port/tools/mod_verify.py` on exactly the files recorded in `index.json`, with the
North American discs and the port version recorded there, and it reported:

- every patch line applying in the game (none skipped);
- every map the mod touches loading and running all its events (trigger regions, Private
  Actions, NPC talk) with no crash, hang, new timeout, new game over or new stand-in, compared
  with the same maps without the mod;
- every battle with an enemy type the mod edits starting and running without a crash.

The maintainer also read the static check's list of risky edits and the mod's README.

A verified mod does what its lines say and doesn't inject anything that breaks the game in
those checks. It isn't a promise about balance, or about every save. **Any change to a verified
mod's files makes it unverified** until it is verified again.

## The rules

- **Data only.** A package holds `mod.json`, the `.patch` files it lists, and at most a
  `README.md`. No images, programs or other binaries, no subfolders, no links. A mod describes
  itself in words.
- **No game data.** The project contains no material from the game discs. A patch line holds
  only the small expected and new values of the format, which `so2_mod.py` reads from your own
  disc. Don't copy anything else from the discs into your package or its README.
- **Written against the North American discs.** Every line's EXPECTED must be what that
  release holds; `so2_mod.py` fills it in from your disc. The automatic check compares each
  line with the North American disc's tables. Once on the list, a mod applies on the European,
  French and German discs too, wherever they hold the same values
  ([Modding](Modding#mods-and-the-releases)).
- **Named after its id.** The folder is `mods/<id>/`, and the id is unique on the list.
- **Within the limits:** 32 patch files of up to 256 KiB, `README.md` up to 64 KiB, `mod.json`
  up to 16 KiB, 1 MiB in all; UTF-8 text.
- **Every risky edit declared** in `mod.json`, with a reason (see
  [Making a Mod](Making-a-Mod#declaring-a-risky-edit)).
- **Your own work**, or made with its author's permission, and you agree to it being
  distributed from the repository under the project's
  [licence](https://github.com/IronJade/Shattered-Stars/blob/main/LICENSE).
- **Never mark it verified yourself.** Only the maintainer does that, and the automatic check
  fails a change by anyone else that adds a verification.

## Submitting, step by step

You need a GitHub account and a copy of the repository on your computer (a fork, cloned with
git) with Python 3.10 or newer, as in [Making a Mod](Making-a-Mod#what-you-need).

1. **Put your package in `mods/<your-mod-id>/`**: `mod.json`, your `.patch` files and, if you
   like, a `README.md`. Try the mod in the game
   ([Making a Mod, Step 5](Making-a-Mod#step-5-try-it-in-the-game)).

2. **Run the static check in strict mode and fix everything it reports:**

   ```sh
   python3 port/tools/mod_check.py --strict mods/<your-mod-id>
   ```

   The pull-request check runs in strict mode, so an undeclared risky edit fails it. If you
   mean one, declare it in `mod.json` with a reason, so the reviewer sees why:

   ```json
   "declared_risks": [{"rule": "door-retarget", "lines": ["changes.patch:4"],
                       "reason": "The shortcut back to Arlia; the old door still works."}]
   ```

3. **Regenerate the index**, and commit it together with your folder:

   ```sh
   python3 port/tools/mod_index.py build
   ```

   It prints how many mods the index holds and how many are verified. Your entry says
   `"verified": false`.

4. **Open a pull request with the mod submission template.** Commit your folder and the index
   on a branch and push it to your fork, for example:

   ```sh
   git checkout -b my-first-mod
   git add mods/my-first-mod mods/index.json
   git commit -m "Add my-first-mod"
   git push origin my-first-mod
   ```

   Then open the pull request on GitHub. On the page where you write it, add
   `?template=mod_submission.md` to the end of the address (or `&template=mod_submission.md`
   if the address already holds a `?`) and press Enter. The form fills with the template: fill
   it in and tick its checklist.

## The template's checklist

The template asks for your mod's id, name and version, what it changes and why, and how you
wrote the lines (the `so2_mod.py` commands, or otherwise). Then it asks you to confirm:

| Checklist item | What it means |
|---|---|
| The package is `mods/<id>/` with `mod.json`, its `.patch` files and at most a `README.md` | No images, programs or other files; the folder named after the id |
| Every patch line was written against the North American discs | `so2_mod.py` reads the expected values from your disc |
| `mod_check.py` reports no errors | Run it with `--strict`, as above, so warnings show too |
| Every risky edit is removed or declared with a reason | The `declared_risks` list in `mod.json` |
| You ran `mod_index.py build` and committed `mods/index.json`, with your entry unverified | Only the maintainer verifies |
| You played the changed places with the mod enabled, and the log shows every line applied | Look for `[mods] <id>/...: ... -> ...` lines (see [Installing and Managing Mods](Installing-and-Managing-Mods#where-to-see-what-the-game-did)) |
| The mod is your own work (or you have permission), and you agree to its distribution under the project's licence | |

Under **What I tested**, list the maps you visited, the shops you opened, the battles you
fought and the saves you used. **For the maintainer** is left for the verification report.

## The automatic check

Every pull request that changes the `mods` folder runs the **mods** check
(`.github/workflows/mods.yml`). It needs no discs and runs four steps:

| Step | What it does |
|---|---|
| Static check of every mod | `port/tools/mod_check.py --all --github --strict`: every package in `mods/`, yours included. Errors and undeclared risky edits fail it |
| mods/index.json matches mods/ | `port/tools/mod_index.py check`: the committed index must be what `build` makes |
| Only the maintainer marks mods verified | `port/tools/mod_index.py guard`: fails if a push adds a verification to `mods/index.json` and wasn't made by the maintainer. Losing a verification (any changed file does that) is fine |
| The checker's own tests | `port/tools/test_mod_check.py` |

### Reading the results

Open your pull request's **Checks** tab and choose the **mods** check.

- **The job summary**, at the top of the run's page, has a **Mod check** table with one row per
  mod: its lines, errors, warnings and declared risks. Below it, each mod with findings gets
  its own list, one entry per finding with its level, rule, file and line:

  > - **warning** `price-zero` changes.patch:6: Resurrection Bottle's price becomes 0: free in shops, worth nothing sold

  Declared risks are listed the same way, followed by "declared:" and your reason, so the
  reviewer can read it.
- **Annotations:** each error and warning is also attached to its file and line, so it shows
  on the pull request's **Files changed** tab next to the line it is about.
- **A failed step's log** says what is wrong. For the index, for example: "mods/index.json
  doesn't match mods/: run `python3 port/tools/mod_index.py build` and commit it (differs for:
  my-first-mod)".

Fix the problem in your branch and push again; the check runs again on each push. You can
reproduce the first step on your computer with
`python3 port/tools/mod_check.py --strict mods/<your-mod-id>`.

## What the maintainer checks

`.github/CODEOWNERS` makes the maintainer (@IronJade) the reviewer of everything in `mods/`.
After the automatic check passes, the maintainer:

1. **Reads** the pull request's changes, the check's job summary (errors, warnings and declared
   risks, with their reasons) and your README.
2. **Runs the mod in the real game** with `port/tools/mod_verify.py`, on a copy of your pull request,
   with the discs and a build of the game:

   ```sh
   SS_DISC1=<disc 1 .cue> python3 port/tools/mod_verify.py mods/<id> --bin port/build/shattered-stars
   ```

   Every run is headless, with scratch settings and no memory card. It:
   - runs the static check first (errors stop it);
   - runs every map your script lines touch, and the map of every shop you edit, through an event
     sweep (every trigger region, Private Action and NPC talk entry) once with the mod and once
     without. A crash, a hang, a new timeout or game over, or a new stand-in with the mod fails;
     other differences, such as a door now leading elsewhere, are listed;
   - starts the first battle of every enemy type you edit, which must run without a crash (a
     mod with item lines gets a battle too, since that loads the item table);
   - checks that every patch line applied in some run. A line that was skipped (its EXPECTED
     didn't match) fails; a line no run reached is a warning;
   - writes `report.md`, which the maintainer pastes into your pull request.
3. **If it passes,** records the verification with
   `python3 port/tools/mod_index.py verify <id> --by IronJade`, commits `mods/index.json` to the pull
   request and merges it. Your mod is now on the list.

If the verification fails, the report says which line or map failed, and you can fix it and
push again.

## Updating a mod

To change a mod that is already on the list:

1. Change its files in `mods/<id>/`. Raise `version` in `mod.json` (for example from `1.0.0`
   to `1.1.0`) so players can tell the versions apart; setup shows both when it asks to
   replace the installed one.
2. Run `python3 port/tools/mod_check.py --strict mods/<id>` again.
3. Run `python3 port/tools/mod_index.py build`. Because the files' sha256 changed, your mod's entry
   becomes `"verified": false`. That is expected.
4. Open a pull request as before.

The maintainer verifies the new version the same way. Until then, the mod is unverified and off
the list. Players update by installing the new `.zip`; see
[Installing and Managing Mods](Installing-and-Managing-Mods#updating-a-mod).
